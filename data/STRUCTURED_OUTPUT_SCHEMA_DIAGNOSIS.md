# Extremely Short Structured Output: Offline Schema Audit

This record is analyzed solely based on the official `response_schema()` and validator within the repository. The previous single-sentence preflight left only safety summaries such as `missing_field:constraints`; the full raw response was not saved, so it cannot be asserted that it was `{}` at the time, nor can other missing fields be retroactively checked. This time, neither the official Schema, the official prompt, the V2 standard answers, nor the local value retrieval and verbatim evidence rules were modified.

## Current Full Structure

- The top-level object has **9 required fields** and forbids additional properties: six core intent fields, `requires_melody_present`, `evidence`, and `constraints`.
- `evidence` is a nested object with **all 7 fields required**, and each value can be a string or `null`. Local validation also requires that evidence for non-empty intents appears verbatim in the original sentence.
- `target_valence`, `target_arousal`, and `trajectory` each use `anyOf` once. The first two accept nullable exact integers or `{relation, value}` range objects; `trajectory` accepts `single_target` / `none` strings or `from_to` path objects. The path can further nest `{from, to}` for `valence` / `arousal`.
- `constraints` is a required array; each item is an object containing three required fields: `evidence`, `classification`, and `polarity`. Even when there are no unsupported conditions, `[]` must still be output.
- `current_valence`, `current_arousal`, `target_melodic_surprise`, `requires_melody_present`, and the seven evidence fields can have null values; the `anyOf` for target ranges also includes a `null` option. The compressed formal schema is approximately **3192 UTF-8 bytes**.

## Simplification points for future research (not implemented in this round)

1. Multiple nested objects, three `anyOf` blocks, and a large number of required nullable fields may increase the difficulty for providers to execute structured outputs. A single extremely short response is not enough to prove that this is the root cause.
2. The JSON Schema for the `trajectory` object branches only requires `type`; local validation also requires at least one path, distinct start and end points, and the end point matching the corresponding target. The schema and local validation enforce constraints at different levels, and schema passing cannot be treated as passing the formal intent card.
3. The schema for `requires_melody_present` allows `false`, but local validation only accepts `true` or `null`; the evidence strings in the schema also do not forbid empty strings, while local validation will reject invalid evidence. These discrepancies need to be reviewed separately, and local rules must not be relaxed just to pass pre-checks.
4. If splitting parsing steps or adjusting the schema is considered in the future, new versioning and regression tests should be established first before evaluating the impact on existing V2 answers and scores. This round of minimal probes is only used to distinguish between "failing even with two fields" and "failing primarily under the complete structure", and will not enter the formal pre-check pipeline.

From now on, missing-field errors will list **all known required field names** at the current level; unknown field names and values additionally generated by the model will not enter the error message. Offline tests simulating `{}` cover all nine top-level fields.
