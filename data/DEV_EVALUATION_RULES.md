# Historical Development Set Evaluation Rules (examples, Non-Formal Test)

This file records the evaluation rules and actual process of the previous original development set, not the current formal scoring standard. Formal candidates have chosen `compact-dev-v2`; future formal evaluations will be scored field by field, by subset, and by valid response according to [`FORMAL_SCORING_V3.md`](FORMAL_SCORING_V3.md). Historical development reports remain as they are.

## Separation of Structure and Intent Validation

A call first checks whether the API returns a parsable complete JSON, then checks whether the required keys and types of the formal Schema are complete, and finally runs local value, verbatim evidence, and constraint validation. Structural completeness does not equal correct intent judgment. A previous single-utterance formal pre-check returned all nine fields, but was rejected at `missing_evidence:trajectory`; it is not a successful pre-check and a success flag cannot be created retroactively.

## Unified Standard for `trajectory` Evidence

- `from_to` explicitly specifies the song arrangement sequence and must have verbatim contiguous evidence in the original utterance.
- `none` indicates that there is no encodable song sequence or emotion/arousal target, and `evidence.trajectory` must be `null`.
- `single_target` is a classification of "has target, no song sequence" derived from clearly defined musical emotion or arousal targets. "No specified sequence" itself often has no identifiable independent phrase to cite, so `evidence.trajectory` can be `null`. If the model provides non-empty evidence, it must still appear contiguously and verbatim in the original utterance.
- Other non-empty intent fields and original-sentence evidence requirements for each unsupported condition remain unchanged. Evidence will not be automatically fabricated, nor will author-approved V2 answers be altered.

## Development Set Pre-fixed Scoring and Stopping Rules

Only use the existing 12 `dev_*` examples and author-approved answers; the development set does not depend on the official test set freeze record. Each sentence is called at most once; stop after three consecutive API or structure/format failures. Evidence failures, out-of-range values in valid structures, and field judgments that pass local validation but mismatch the ground truth are logged separately and not conflated as format failures.

The six core fields report correct counts / total 12 items, correct counts / called items, and correct counts / locally valid items respectively; uncalled sentences are listed as "unfinished" in the 12-item coverage column, not model judgment errors. Also list the full card, `requires_melody_present`, unsupported condition original word sets, `cannot_guarantee_constraint` return status, and keyword baselines. Failed calls are counted in the called end-to-end denominator, but are not treated as model false positives or false negatives for unsupported condition original words; original word hits, false positives, and false negatives are calculated only for valid outputs. Costs are estimated based on available tokens and model pricing.

Evaluation requests send only the development sentence original text, fixed runtime system prompt, and complete official Schema; ground truth answers are not sent. Reports and per-sentence traces retain only case IDs, fixed error categories and field names, counts, and tokens, without saving complete model responses or unknown fields and values generated by the model. Result files are located at `reports/dev_evaluation.*`; they are not official test scores and will not create `data/connection_preflight.json`.
