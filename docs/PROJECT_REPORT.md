# From an Everyday Feeling to a Three-Song Path

## Problem and significance

People often know how they feel but not how to describe the music they want. “I need something that helps me calm down” is natural language, not a filter menu. My project asks whether a listener can express such a need in ordinary Chinese and receive a small, ordered set of songs with an intelligible reason for each choice. Its longer-term ambition is aesthetic discovery: helping listeners encounter melodic differences they might otherwise miss, through exploration rather than overt instruction. This course prototype tests a narrower question. It cannot show that anyone's musical taste improved.

The immediate alternative is a conventional keyword rule or a manually curated list. Both can be useful; the question is whether a language model adds enough interpretation to justify its extra cost and failure modes. I therefore built a comparator rather than assuming the model is inherently better. The primary user is a commuter or casual listener who wants new music without knowing technical terms. The interaction is deliberately small: one text request, then either three ordered track-page links or a clear explanation that the catalog cannot guarantee a requested condition. There is no account, player, or uploaded audio.

## Design and implementation

The runtime model converts the request into an intent card: current and desired emotional valence, current and desired arousal, desired melodic surprise, and whether a genuine song-order trajectory was specified. It also returns evidence phrases copied from the original request. A compact output format is converted to the project's V2 structure, and local code rejects missing fields, invalid values, unsupported paths, or evidence absent from the source text. A separate flag handles a request for a discernible melody. This division matters: I rent language interpretation through OpenRouter but own the catalog, validation, scoring, and ranking logic. It avoids training a model on this small dataset, yet creates a network dependency and sends each live request to an external provider. The code does not infer song qualities from titles.

The catalog contains 35 MTG-Jamendo tracks with external links and author-reviewed labels for valence, arousal, melody presence, and melodic surprise. Hard ranges and the melody-presence requirement are filters. Relevant labels then receive weighted similarity scores; an explicit three-step request sets start, middle, and end targets. A request involving genre, loudness, language, or tempo cannot be guaranteed with this catalog, so the system refuses rather than pretending a nearby label proves compliance. Refusal is honest, though not always satisfying. Audio is neither hosted nor redistributed; current track-level audio rights were not independently verified for reuse.

## Evidence and results

The evaluation uses 42 author-reviewed Chinese request examples: 12 for development and 30 for formal testing. They were not collected from participants. The formal answers and scoring rules were approved and frozen before the completed run; the freeze record contains timestamps and file hashes. The first attempted formal run stopped after three connection failures, with no valid cards. I preserved that failed run rather than turning its zeros into an accuracy claim. After a separate successful connectivity check, a second formal run called the same selected model once for each of the 30 frozen requests. All 30 returned structurally complete outputs, and 28 passed local validation. The two invalid cards remain in end-to-end denominators.

The exact six-field card score was **11/30** for the model versus **12/30** for the keyword baseline. That one-case difference is not evidence of general superiority for either approach. Per-field results reveal more. The model found the correct trajectory in **23/30**, compared with **18/30** for keywords. Its target-valence field was exact in **22/30**, versus **20/30**. However, target arousal was exact in only **16/30**, versus **23/30**. Looking at the 11 requests whose approved target-valence field was actually stated, the model was correct on **7/11** and the baseline on **1/11**. On the 19 requests without a stated target valence, the baseline's conservative empty answer was correct on all 19. This contrast is the core finding: richer interpretation helps some explicit requests but also creates unwarranted inferences. The strict full-card metric exposes that trade-off, yet would hide it if reported alone.

The routing audit of saved cards found **21/30** requests yielding three linked tracks, **7/30** refusing an unguaranteed condition, and **2/30** invalid cards; none failed solely because the catalog lacked three eligible tracks. That audit establishes a working pipeline, not musical quality. For a separate author-only listening check, I reviewed five ready playlists selected at predetermined positions in ID order and the first two refusals. All 15 linked positions played and I personally liked all 15, but only **10/15** fully fit their request, **4/15** partly fit, and **1/15** did not. Just **1/5** complete playlists fully met its request. Liking a track clearly cannot substitute for judging whether it answers the listener's words.

## Critical reflection

The strongest counterexample is a breakup request that says the person hopes to feel better after crying. The model treated this as an instruction to make the three songs change from sad to happy. The resulting transition could sound natural while still misreading the request: a person's hoped-for recovery is not necessarily a playlist ordering rule. Another review disputed the high-arousal catalog label of “Fly So High” in an anger-release playlist. This is a data-quality issue, not just an inference issue. A third case showed that a refusal can be technically correct yet provide an incomplete explanation or no gentler alternative.

I also learned not to confuse interface reliability with semantic accuracy. The initial, more elaborate response structure often failed validation. A compact format made complete output more reliable in development, but did not automatically improve full-card correctness. Network restrictions then caused the first formal run to stop before useful results. I separated the failed and completed runs, kept one call per request, and reported both local-validity and intent scores. The completed 30 requests used 44,616 input and 4,887 output tokens, with an estimated provider-list-price cost of **US$0.025602**; this is an estimate, not a billing receipt.

The evidence has real limits. Because the requests were not collected from participants, these examples cannot establish prevalence or performance with real listeners. Some examples had informed earlier rule discussion, so freezing their answers does not make this a pristine unseen-design benchmark. Exact-match scoring can punish defensible alternatives; the keyword baseline is particularly strong when fields are unstated. The listening sample is small, chosen systematically rather than randomly, and rated by one person without a competing recommendation system. The 35-track catalog is too narrow to satisfy many ordinary constraints. I can claim a reproducible end-to-end mechanism and an informative failure analysis, not that it improves discovery or aesthetic judgment in the world today.

The next step would be to recheck disputed labels, add properly sourced song attributes only where permissions and evidence allow, test a clarification or constraint-relaxation interaction, and compare recommendations with a baseline in a consented listener study. Success should mean that listeners discover music they value over time—not merely that the model can fill a JSON object.
